# 退款申请预审

> 示例 Skill。演示：**判断留在这里，事实全部去 Wiki**。
> 从 `wiki/topics/example-refund-window.md` 蒸馏于 2026-10-12。

## 0. 一句话

把一条退款工单分成「可直接批准 / 需人工审批 / 应拒绝」三类，并给出可核对的依据。

## 1. 何时使用 / 何时不要使用

**使用**：

- 任务是审核退款申请、或起草退款答复
- 输入包含订单号、签收时间、商品品类

**不要使用**：

- 价格调整、换货、补发 → 走对应流程
- 物流赔付 → 走物流工单
- 涉及跨境订单 → 口径未确认，直接转人工

> 边界先划清：**不确定的品类一律转人工，不要自己套规则。**

## 2. 判断框架

| 条件 | 判断 | 动作 |
|---|---|---|
| 品类属于例外清单 | 不适用无理由退款 | 转人工审批 |
| 品类正常，且申请时间在窗口内 | 符合条件 | 批准，附依据 |
| 品类正常，申请时间超窗口但在宽限内 | 可特批 | 转人工审批，注明超期天数 |
| 超窗口且超宽限 | 不予受理 | 拒绝，附条款依据 |
| 签收时间缺失 | 无法判定 | **不要猜**，要求补充证据 |

## 3. 执行步骤

1. **取数**
   - 输入：订单号、商品品类、签收时间、申请时间
   - 完成判据：签收时间与申请时间都拿到了；缺一个就停下来要
2. **判定品类**
   - 动作：比对例外清单（**去 Wiki 查，不要凭记忆**）
3. **算窗口**
   - 动作：按 Wiki 的起算点与长度判定
   - 注意：不看下单时间、不看发货时间
4. **出结论**
   - 输出：分类 + 依据引用 + open_questions + falsifiers

## 4. 好坏标准

- **合格**：每个结论都带 `wiki:` 引用；时间口径写明"以签收时间为准"；例外品类说得出是哪一条
- **不合格**：只给"建议批准"，没有依据；或把下单时间当起算点
- **常见偷懒**：签收时间缺失时按"客户说得有道理"批准 —— 这是把不确定性外包给话术

## 5. 边界与例外

- **例外**：客户提供了签收异议凭证（如物流异常签收截图）→ 一律转人工
- **已知不适用**：跨境订单
- **人工兜底**：任何"窗口边界 ±1 天"的申请，转人工而不是自行判定

## 6. 下钻契约

### 必须查（禁止凭记忆回答）

- 退款窗口的**起算点与长度** → `wiki:topics/example-refund-window#refund-window`
- **例外品类清单** → `wiki:topics/example-refund-window#exceptions`
- 超期特批的**宽限期** → `wiki:topics/example-refund-window#refund-window`

### 什么时候不必查

- 只是判断"要不要转人工"这类流程性动作

### 查询预算

- 最多读 2 个条目；先读 TL;DR，摘要不够再读 `#refund-window` / `#exceptions` 两节

### 引用格式

```
依据：`wiki:topics/example-refund-window#refund-window`
```

## 7. 冲突规则

- **事实**（天数、起算点、品类清单）以 **Wiki** 为准。
- **判断**（该批准还是转人工）以 **本 Skill** 为准。
- **冲突时停下来报告**，贴出两边原文与出处，不要自行裁决。

## 8. 输出格式

1. **方案**：分类 + 理由 + 依据引用
2. **open_questions**：例 `[open] 该品类是否属于定制类 → 去 wiki:topics/example-refund-window#exceptions 核实`
3. **falsifiers**：例「若签收记录显示实际签收日晚于工单填写的日期，则窗口判定需重算」
